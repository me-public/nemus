# Cloud / IaC for Nemus — design plan

**Status:** P0 design + P1 scaffold started (`packages/cloud`, forge-auth seam).
**Goal:** give Nemus an *optional* way to run a workspace + coding agent on the
user's own infrastructure — clone repos, run the agent, open a PR, drive it to
green — vendor-neutral, provider-pluggable, defined as IaC. The value of
workspace-manager's cloud, generalized for open source.

## Guiding constraint

Nemus core is **local-first, vendor-neutral, zero cloud/AWS/Melio**, and CI
enforces it. Any cloud feature must preserve that. Therefore cloud ships as a
**separate, opt-in package `@nemus-cli/cloud`** (npm workspace under
`packages/`), with its own (heavier) deps and CI. Core `@nemus-cli/nemus` never
imports it; installing the CLI pulls in none of it.

This is a **re-architecture, not a port**: workspace-manager's cloud is ~39 files
of Melio/AWS coupling (`@melio/mdk`, buzaglo, nemala, shared VPC/ECR,
`@melio/secrets`, ECS-on-EC2, SSM, hosted UI, Slack). We keep the *ideas*, drop
the coupling.

## Five ideas that make it generic

1. **The OCI image is the portability boundary.** Push *all* logic into a
   provider-agnostic runner image that takes only env; keep runners dumb. Every
   backend (Docker, Fly, Fargate, Cloud Run, k8s, bare VM) can "run an OCI image
   with env and stream logs," so a new provider is trivial.
2. **Split provisioning from execution.** IaC ("stand up a place that can run
   tasks") and task execution ("run one job") are different lifecycles → two
   plugin points, joined by a small, versioned, serializable **Target
   Descriptor** (JSON). Provision once, run many times; or hand-write a
   descriptor to bring-your-own infra and skip IaC entirely.
3. **Capabilities over lowest-common-denominator.** Backends declare what they
   support; features degrade gracefully (like `WCLOUD_UI_AUTH` refusing unknown
   modes) instead of designing to the weakest backend.
4. **Plugins via a registry, not a `switch`.** Each backend is
   `@nemus-cli/cloud-<name>` implementing the interfaces, resolved by name from
   config — same shape as `AGENT_ORDER`. Ship `docker` in-box; the rest opt-in;
   third parties publish without touching core.
5. **One config file, provider-shaped by schema.** Generic keys at the top
   (validated by core), a provider-namespaced block validated by that plugin's
   own Zod schema.

## Interfaces (the seams)

```ts
interface Runner {
  id: string;
  capabilities: { exec; logStream; persistentDisk; secretStore; portForward };
  launch(spec: TaskSpec, target: TargetDescriptor): Promise<Handle>;
  status(h: Handle): Promise<Status>;
  logs(h: Handle): AsyncIterable<LogLine>;
  exec?(h: Handle, argv: string[]): Promise<ExecResult>; // gated by capability
  stop(h: Handle): Promise<void>;
}

interface Provisioner { up(cfg): Promise<TargetDescriptor>; down(t: TargetDescriptor): Promise<void>; }

interface TaskSpec {                 // 100% provider-neutral
  image: string; env: Record<string,string>; secrets: SecretRef[];
  command?: string[]; resources: { cpu; memoryMB; diskGB? };
  labels: Record<string,string>;
}

interface TargetDescriptor {         // the IaC <-> execution contract; small + versioned
  version: 1; runner: string;        // 'docker' | 'fly' | 'aws-fargate' | ...
  region?: string; endpoint?: string; cluster?: string;
  secretBackend?: string; extra?: Record<string, unknown>;
}

interface GitForge { openPR(...); getChecks(...); comment(...); }     // github | gitlab
interface SecretSource { resolve(ref: SecretRef): Promise<string>; } // env | dotenv | gh | vault | 1password | provider-native
interface ForgeTokenSource { id: string; getToken(scope?): Promise<{token; expiresAt}>; }
```

Core orchestration (run / logs / report-back / CI-loop) is written **only**
against these — it never imports a cloud SDK. Litmus test for every line:
*"Would this still compile if the only backend were a local Docker socket?"*

## The runner image (env-only contract)

```
env in:  NEMUS_REPOS, NEMUS_TASK, NEMUS_AGENT (+ creds), NEMUS_FORGE,
         GIT_TOKEN | GITHUB_APP_*, GIT_HOST, REPORT_MODE
does:    clone -> two-phase plan/execute agent -> open PR (GitForge)
         -> stream logs to stdout -> write result.json -> exit code
```
Nothing AWS. Reuse the genuinely-good, vendor-neutral parts of
workspace-manager's `infra/docker`: the **two-phase plan/execute** flow and the
**`run_bounded` inactivity watchdog**.

## Forge auth (GitHub App) — resolved

The one auth seam is **`ForgeTokenSource`** (implemented in `packages/cloud`).
GitHub App is *one* implementation; nothing downstream knows it isn't a PAT.

- `pat` — static token; zero config; works for every forge/runner.
- `github-app` — mints short-lived, **least-privilege**, **auto-refreshing**
  installation tokens (dependency-free RS256; auto-discovers the installation by
  owner). Attribution to `${app}[bot]`.

**Private-key placement is a policy, not a default** (same class serves all):

| Policy | Key lives on | Refresh | Use when |
| --- | --- | --- | --- |
| **A. client-side (default)** | control plane; only the 1h token is injected | control channel | attached, PR-sized runs |
| **B. in-task** | task (via provider secret store) | task self-refreshes | long, fire-and-forget runs |
| **C. broker** | one small long-lived service | task re-requests | org-scale headless |

Gotchas carried over: **GitHub App tokens cannot auth to `npm.pkg.github.com`** —
private `@scope` installs need a separate classic PAT (`read:packages`), its own
`SecretSource`, never conflated with the git token. Keys are read from a secret
store into memory only; never written to an image layer or logs; tokens redacted
in log streams. PAT is always the zero-config fallback.

## Port vs. abstract vs. drop (from workspace-manager)

| From workspace-manager | Decision |
| --- | --- |
| `mdk/template.ts` (`@melio/mdk` CDK) | **Drop** → OpenTofu/Terraform modules |
| buzaglo, nemala, shared VPC/ECR, Apono | **Drop** (Melio-only) |
| ECS-on-EC2 + SSM exec + hosted UI + IAM/Vault auth | **Drop** → Fargate/Fly/Docker |
| `@melio/secrets` / Secrets Manager | **Abstract** → `SecretSource` |
| two-phase agent, `run_bounded`, CI-loop, report-back | **Port** (vendor-neutral) |
| GitHub App token minting | **Abstract** → `ForgeTokenSource` (done, P1) |
| Slack Socket Mode control | **Defer** (optional plugin) |

## Roadmap

- **P0 — Design & decisions.** _(this doc)_
- **P1 — Package + forge-auth seam + execution seam.** `@nemus-cli/cloud` scaffold;
  `ForgeTokenSource` with `pat` + `github-app`; **`Runner`/`Provisioner` interfaces**
  with neutral `TaskSpec`/`TargetDescriptor`/`Capabilities`, a **registry** (resolve
  by name, like `AGENT_ORDER`), and the **in-box local Docker runner** (`DockerRunner`,
  dependency-free, needs no cloud account) — launch/status/logs/exec/stop, unit-tested
  with mocked CLI boundaries. **← done.** Next: the **agent OCI image** (clone →
  two-phase agent → open PR → stream logs → result.json) the runner launches.
- **P2 — IaC + first cloud provider.** OpenTofu modules; `nemus cloud init/up/down`;
  first cloud target (Fly *or* AWS Fargate).
- **P3 — report-back (draft PR) + bounded CI-loop** over `GitForge`.
- **P4 — more providers (plugins), optional Slack, optional hosted UI.**

## Decisions (locked / open)

- **Locked:** separate `@nemus-cli/cloud` package (npm workspaces monorepo);
  OCI image as portability boundary; provision/execution split via Target
  Descriptor; capability-based degradation; forge auth via `ForgeTokenSource`
  with A/B/C key placement.
- **Open (pick before P2):** IaC tool (**OpenTofu** recommended vs Pulumi/CDK);
  first cloud provider (**Fly** for OSS simplicity vs **Fargate** for
  enterprise); agent auth in cloud (API-keys-in-secrets vs cloud-native IAM).

## Anti-patterns to avoid

- Don't invent a universal IaC DSL — that was the `@melio/mdk` mistake. Delegate
  to real IaC tools; standardize only their inputs/outputs (the descriptor).
- Don't design to the weakest backend — use capabilities + graceful degradation.
- Don't let provider quirks (VPC/subnets, Fly org) leak into core — contain them
  in the provider's config block + Provisioner.
- One credential-resolution chain, not per-provider bespoke auth.
- Keep the Target Descriptor small + versioned — it's the portability contract.
